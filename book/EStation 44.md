# معماری بالادستی E-Station

## ۱. پیش‌ران‌های معماری (Architectural Drivers)
- **راه‌اندازی سریع و کم‌هزینه:** استقرار اولیه بر بستر یک هاست اشتراکی ویندوز با منابع محدود (بدون Redis، سرویس‌های پس‌زمینه جداگانه، یا Container Orchestration).
- **داده‌های جمع‌سپاری‌شده:** مدل اطلاعاتی باید بتواند از مشارکت کاربران تغذیه شود و با سازوکارهای خودترمیمی کیفیت داده‌ها را حفظ کند.
- **چند‌سکویی (Multi-platform):** یک پایگاه کد مشترک برای رابط کاربری تحت وب (PWA) و اپلیکیشن موبایل (اندروید و ویندوز).
- **مقیاس‌پذیری آتی:** معماری باید امکان مهاجرت به زیرساخت‌های ابری و مقیاس‌پذیر را بدون بازنویسی اساسی فراهم کند.
- **امنیت و اعتماد:** احراز هویت و اعتبارسنجی کاربران، محافظت از داده‌ها و جلوگیری از تقلب در رأی‌گیری.

## ۲. نمای کلی سیستم (System Overview)
E-Station به صورت یک **سیستم توزیع‌شده سبُک** طراحی شده که از چهار بخش اصلی تشکیل می‌گردد:

1. **Backend API (مغز سیستم):** یک سرویس ASP.NET Core که تمام منطق کسب‌وکار را در خود جای داده و از طریق REST API در دسترس کلاینت‌ها قرار می‌گیرد.  
2. **Shared UI Library (کتابخانه مشترک رابط کاربری):** شامل کامپوننت‌ها و صفحاتی که در هر دو پلتفرم کلاینت (وب و موبایل) استفاده می‌شوند.  
3. **Web Application (PWA):** یک کلاینت Blazor WebAssembly که در مرورگر اجرا شده و قابلیت نصب و کار آفلاین محدود را دارد.  
4. **Mobile Application (MAUI Hybrid):** یک برنامه بومی برای اندروید و ویندوز که همان رابط کاربری مشترک را درون یک WebView محلی نمایش می‌دهد و از قابلیت‌های دستگاه (مانند GPS) بهره می‌گیرد.

تمامی این بخش‌ها با API مرکزی ارتباط برقرار می‌کنند. در استقرار واقعی، فایل‌های Web PWA به‌عنوان محتوای استاتیک از همان سرور API سرو می‌شوند تا پیچیدگی میزبانی به حداقل برسد.

## ۳. سبک‌های معماری به‌کاررفته
- **معماری لایه‌ای (Layered Architecture) بر اساس اصول Clean Architecture:** تفکیک نگرانی‌ها به گونه‌ای که منطق کسب‌وکار در مرکز قرار گیرد و وابستگی‌ها به سمت بیرون کاهش یابند.  
- **Domain-Driven Design (DDD) در حد نیاز:** از مفاهیمی مانند Aggregate، Entity، Value Object و Bounded Context برای سازمان‌دهی منطق پیچیده حوزه صحت‌سنجی و امتیازدهی استفاده شده است. (جزئیات در مستندات دامنه موجود است)  
- **CQRS سبُک (بدون Event Sourcing):** تفکیک عملیات خواندن و نوشتن برای برخی از بخش‌ها به‌منظور سادگی و کارایی.  
- **پردازش رویداد درون‌فرآیندی:** به دلیل نبود زیرساخت پیام‌رسان خارجی، رویدادهای دامنه (مانند ثبت بازخورد) به‌صورت همزمان یا در پس‌زمینه‌های سبک داخل همان پروسه مدیریت می‌شوند.

## ۴. تجزیه کارکردی سطح بالا (High-Level Functional Decomposition)
بر اساس نیازهای کسب‌وکار، سیستم به **پنج بافت (Context) اصلی** تقسیم می‌شود که هر یک سرویس‌های خاص خود را دارد (نحوه ارتباط و مرزهای دقیق در مستند Bounded Contextها ذکر شده است):

- **بافت مدیریت ایستگاه‌ها (Station Management Context):** هسته‌ی اصلی داده‌های فیزیکی، فنی و چرخه عمر ایستگاه‌های شارژ، همچنین مدیریت ادعای مالکیت تجاری (توسط اپراتورهای رسمی). 
- **بافت اکتشاف و جستجو (Station Discovery Context):** فراهم کردن امکان جستجوی فوق‌سریع و مبتنی بر نقشه برای کاربران.  
- **بافت پالایش محتوا (Crowdsourced Curation Context):** مدیریت خرد جمعی، دریافت بازخوردها و رأی‌های کاربران، اعمال قواعد تأیید/رد جمعی.  
- **بافت تجربه کاربری (User Experience Feedback Context):** ثبت نظرات و تجربیات شخصی کاربران از ایستگاه‌ها. 
- **بافت محصور انگیزش و اعتبار (User Gamification Context):** موتور رشد پلتفرم. این بافت با مدیریت امتیازات، نشان‌ها و تعیین سطح کاربران، انگیزه تولید اطلاعات دقیق را فراهم می‌کند.
- **بافت هویت و دسترسی (Identity & Access Context):** احراز هویت، مجوزدهی و پروفایل.  
- **بافت اعلان‌ها (Notification):** مدیریت کانال ارتباطی سامانه با کاربران، آگاه‌سازی درون‌برنامه‌ای کاربران از رویدادهای مهم.

این بافت‌ها در حال حاضر در یک Deployment Unit (پایگاه کد و دیتابیس واحد) پیاده‌سازی می‌شوند، اما از نظر مفهومی مرزهای مشخصی دارند که امکان شکستن آنها در آینده را فراهم می‌کند.

## ۵. تصمیمات کلان فناوری (Key Technology Decisions)
- **پایگاه داده رابطه‌ای بدون پشتیبانی فضایی:** استفاده از SQL Server (یا PostgreSQL) بدون قابلیت Spatial برای انجام کوئری‌های جغرافیایی کارا.  
- **احراز هویت مبتنی بر JWT:** تأمین امنیت API بدون نیاز به سشن سرور.  
- **ذخیره‌سازی توکن در کلاینت:** استفاده از محل ذخیره‌سازی امن هر پلتفرم (حافظه محافظت‌شده مرورگر، SecureStorage در موبایل).  
- **کَش درون‌حافظه‌ای:** برای کاهش بار پایگاه داده در کوئری‌های پرتکرار (بدون Redis).  
- **ثبت وقایع (Logging) مبتنی بر فایل:** با کتابخانه‌ای که امکان چرخش و بایگانی فایل‌های لاگ را دارد؛ با امکان تعویض با مقصد پایگاه داده در صورت محدودیت هاست.

## ۶. استقرار و توپولوژی (Deployment Topology)
- **محیط تولید:** یک هاست اشتراکی ویندوز با IIS که یک Application Pool میزبانی‌کننده ASP.NET Core را اجرا می‌کند.
- **پایگاه داده:** یک نمونه SQL Server روی همان سرور یا یک سرور پایگاه داده اشتراکی.
- **محتوای استاتیک:** فایل‌های Web PWA درون پوشه `wwwroot` کنار API قرار گرفته و توسط همان IIS سرو می‌شوند.
- **اپلیکیشن موبایل:** مستقیماً با همان API از طریق اینترنت ارتباط برقرار می‌کند.

این چینش بهره‌وری کامل از منابع محدود هاست را فراهم کرده و هزینه‌های عملیاتی را حداقل نگه می‌دارد. با رشد سیستم، می‌توان API را به یک سرور اختصاصی یا ابر انتقال داد و کلاینت‌های وب را از طریق CDN توزیع کرد، بدون آنکه نیاز به تغییر در ساختار کد باشد.

## ۷. ویژگی‌های کیفی (Quality Attributes)
- **کارایی (Performance):** استفاده از Spatial Indexها برای جستجوی نزدیک‌ترین ایستگاه‌ها، کش استاتیک برای فایل‌های PWA، و پاسخ‌های فشرده‌سازی‌شده.
- **قابلیت اطمینان (Reliability):** فرآیندهای صحت‌سنجی جمعی خطای داده‌های ایستگاه را به حداقل می‌رسانند. در صورت ریست Application Pool، کارهای پس‌زمینه در تماس‌های بعدی کاربران جبران می‌شوند.
- **امنیت (Security):** تمام درخواست‌ها از HTTPS عبور می‌کنند، توکن‌های دسترسی دارای طول عمر محدود هستند و بازخوردهای کاربران بر اساس وزن اعتبار آن‌ها ارزیابی می‌شود تا از حملات تقلبی جلوگیری شود.
- **نگهداشت‌پذیری (Maintainability):** به لطف تفکیک لایه‌ها و بافت‌ها، تغییرات در یک بخش کمترین تأثیر را بر سایر بخش‌ها دارد. مستندات جداگانه هر بخش نیز درک سیستم را آسان می‌سازد.
- **مقیاس‌پذیری (Scalability):** معماری کنونی محدودیت‌های هاست اشتراکی را می‌پذیرد، اما با الگوی CQRS و بافت‌های مجزا، آمادگی خرد شدن به میکروسرویس‌ها در صورت نیاز وجود دارد.
