### سند دستورالعمل پیاده‌سازی لایه دامنه (Domain Layer Implementation Guidelines)
**هدف:** اجرای دقیق لایه Domain بر اساس اصول معماری تمیز (Clean Architecture) و طراحی مبتنی بر دامنه (DDD) با رویکرد Pure C# و مدل‌سازی غنی.
در توسعه تمامی کلاس‌ها، موجودیت‌ها و منطق‌های این لایه، قوانین زیر را بدون استثنا رعایت کنید:
#### ۱. اصل خلوص و وابستگی (Domain Purity)
 * **صفر وابستگی خارجی:** لایه Domain هسته مرکزی نرم‌افزار است. هیچ‌گونه وابستگی به دیتابیس، فریم‌ورک‌های وب، کتابخانه‌های ORM (مانند Entity Framework Core) یا لایه‌های بیرونی مجاز نیست.
 * **حذف Data Annotations:** از هیچ‌گونه Attribute مربوط به پایگاه داده (مانند [Key], [Table], [Required]) روی کلاس‌ها استفاده نکنید. کلاس‌ها باید **Pure POCO** باشند.
#### ۲. پکیج‌های استاندارد لایه
تنها استفاده از پکیج‌های زیر (یا پیاده‌سازی‌های مشابه داخلی) برای مدیریت جریان برنامه مجاز است:
 * استفاده از پکیج **ErrorOr** برای پیاده‌سازی الگوی نتیجه (Result Pattern).
 * استفاده از پکیج **Throw** برای پیاده‌سازی Guard Clauses و اعتبارسنجی سریع داده‌ها در Constructorها.
#### ۳. مدل دامنه غنی (Rich Domain Model)
 * **مدل‌های کم‌خون (Anemic Models) اکیداً ممنوع:** ایجاد کلاس‌هایی که صرفاً مجموعه‌ای از public get/set هستند، ممنوع است.
 * **کپسوله‌سازی وضعیت (State Encapsulation):** تمامی Propertyهای موجودیت‌ها باید دارای private set یا private init باشند.
 * **تغییر وضعیت معنادار:** تغییر State موجودیت‌ها تنها باید از طریق فراخوانی متدهای Public با نام‌های توصیفی و بیزینسی (مثلاً CancelSubscription به جای UpdateStatus) انجام شود.
#### ۴. مدیریت جریان منطقی (Result Pattern)
 * **ممنوعیت Exception برای بیزینس لاجیک:** از throw new Exception برای نقض قوانین کسب‌وکار استفاده نکنید. Exceptionها فقط برای خطاهای سیستمی و غیرمنتظره هستند.
 * **خروجی متدها:** تمامی متدهایی که امکان شکست بیزینسی دارند (و همچنین Factory Methodهای سازنده کلاس)، باید خروجی از نوع ErrorOr<T> یا ErrorOr<Success> داشته باشند.
 * **خطاهای توصیفی:** خطاها را به صورت شفاف با ذکر نوع خطا در دامنه تعریف کنید (مانند Error.Validation(...) یا Error.Conflict(...)).
#### ۵. حفاظت از قوانین ثبات (Protecting Invariants)
 * همیشه پیش از اعمال هرگونه تغییر یا ایجاد شیء جدید، قوانین کسب‌وکار (Invariants) را بررسی کنید.
 * مثال: پیش از افزودن یک وظیفه، بررسی کنید که آیا محدودیت روزانه تکمیل شده است یا خیر؟ اگر بله، فوراً یک خطای بیزینسی متناسب برگردانید.
#### ۶. ریشه‌های تجمیع (Aggregate Roots) و مرزها
 * **ارتباط با دنیای بیرون:** لایه‌های بیرونی (مانند Application) فقط و فقط مجاز به تعامل با کلاس‌های **Aggregate Root** هستند.
 * **مدیریت فرزندان:** تغییرات در موجودیت‌های داخلیِ (Entities) یک Aggregate، باید توسط متدهای خود Aggregate Root مدیریت و مسیریابی شود تا یکپارچگی تراکنش حفظ گردد.
#### ۷. رویدادهای دامنه (Domain Events) و سازگاری نهایی

- **ثبت رویداد:** تغییرات مهم وضعیت باید به صورت `IDomainEvent` مدل‌سازی شده و از طریق متد `AddDomainEvent` به لیست داخلی `_domainEvents` اضافه شوند.
    
- **ممنوعیت انتشار مستقیم:** لایه دامنه هرگز مجاز به فراخوانی Bus، MediatR یا هرگونه Pub/Sub نیست.
    
- **مسئولیت زیرساخت:** لایه زیرساخت موظف است پس از موفقیت آمیز بودن عملیات ذخیره‌سازی (Commit تراکنش)، این رویدادها را از Aggregate خوانده و **الزاماً از طریق الگوی Outbox** یا یک پردازش ناهم‌زمان قابل اطمینان، منتشر کند تا در صورت بروز خطا در پردازش رویداد، تراکنش اصلی برگشت نخورده و سازگاری نهایی سیستم حفظ شود.
    
- **پاک‌سازی:** پس از انتشار موفق، زیرساخت باید متد `ClearDomainEvents` را برای جلوگیری از پردازش مجدد فراخوانی کند
