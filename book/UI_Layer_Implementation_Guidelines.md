### سند دستورالعمل پیاده‌سازی لایه رابط کاربری (UI Layer / Blazor WebAssembly Implementation Guidelines)

**هدف:** پیاده‌سازی رابط کاربری بر بستر **Blazor Hosted WebAssembly**، با تمرکز بر کامپوننت‌محوری، کارایی بارگذاری در مرورگر، حداقل وابستگی به جاوااسکریپت، و پشتیبانی کامل و بومی از زبان فارسی و چیدمان راست‌به‌چپ (RTL).
لطفاً در توسعه صفحات (Pages)، کامپوننت‌ها (Components) و ساختار پروژه Client، قوانین زیر را به دقت رعایت کنید:

#### ۱. معماری بارگذاری در Blazor Hosted WebAssembly

* **صفحه بارگذاری اختصاصی:** به‌جای پیام پیش‌فرض `Loading...`، یک صفحه Loading سفارشی (با برندینگ و اسکلتون‌های UI) طراحی کنید که تا زمان کامل شدن بوت WebAssembly (`Blazor.start`) نمایش داده شود.
* **Lazy Loading اسمبلی‌ها:** برای ماژول‌های حجیم یا کمتر پراستفاده (مثلاً بخش گزارش‌گیری یا پنل مدیریت)، از قابلیت Lazy Loading اسمبلی‌ها (`<LazyAssembly>` در `.csproj` و `Router` با `OnNavigateAsync`) استفاده کنید تا حجم اولیه دانلود کاهش یابد.
* **Trimming و انتشار بهینه:** گزینه‌های `PublishTrimmed`، فعال‌سازی فشرده‌سازی Brotli و بررسی دوره‌ای حجم فایل‌های `.dll` منتشرشده در فرآیند انتشار الزامی است.
* **مدیریت وضعیت آفلاین/خطای شبکه:** برای Hosted WASM (بدون Server-Side Rendering)، وضعیت قطع ارتباط با API را با یک کامپوننت مشترک نمایش پیام خطا مدیریت کنید؛ کاربر هرگز نباید با صفحه سفید یا Exception خام مواجه شود.
* **Caching با HttpClient:** برای داده‌های نسبتاً ثابت (مانند لیست‌های مرجع)، از الگوی Cache در سطح سرویس‌های Client (به همراه معتبرسازی زمانی) استفاده کنید تا فراخوانی مکرر API کاهش یابد.

#### ۲. پکیج‌ها و ابزارهای استاندارد لایه

* استفاده از **Bootstrap 5** صرفاً برای Grid System، Utility Classes (spacing، flexbox) و کامپوننت‌های پایه (Modal، Dropdown، Toast).
* استفاده از **CSS Isolation** توکار Blazور (`Component.razor.css`) به عنوان روش اصلی استایل‌دهی اختصاصی هر کامپوننت.
* استفاده از **Mapster** یا مدل‌های سبک Client-side برای تبدیل پاسخ‌های Contracts به ViewModelهای مخصوص UI (در صورت نیاز).
* برای LocalStorage از پکیجی مانند **Blazored.LocalStorage** (یا پیاده‌سازی داخلی مشابه پشت یک Interface) استفاده کنید، نه فراخوانی مستقیم و پراکنده `IJSRuntime` در کامپوننت‌ها.

#### ۳. اولویت C# بر جاوااسکریپت (Minimal JS Interop)

* **قاعده پایه:** هر نیازی که با قابلیت‌های توکار Blazor (Data Binding، `EventCallback`، `EditForm`، `Two-way Binding`) قابل حل است، **نباید** با جاوااسکریپت پیاده‌سازی شود.
* **JS فقط برای APIهای مرورگر:** استفاده از JavaScript صرفاً برای دسترسی به قابلیت‌هایی که در .NET/Blazor در دسترس نیستند مجاز است (مثلاً برخی APIهای پیشرفته مرورگر، کتابخانه‌های چارت شخص ثالث، یا انیمیشن‌های پیچیده CSS/DOM).
* **JS Isolation:** در صورت نیاز اجتناب‌ناپذیر به JS، از **JavaScript Isolation** با ماژول‌های ES6 (`import IJSObjectReference`) استفاده کنید؛ فایل `.js` باید هم‌جوار با کامپوننت مربوطه (`Component.razor.js`) قرار گیرد، نه در یک فایل عمومی و بزرگ `site.js`.
* **Dispose صحیح:** هر `IJSObjectReference` گرفته‌شده باید در `DisposeAsync` کامپوننت آزاد شود تا از نشت حافظه در طول عمر SPA جلوگیری شود.

#### ۴. استفاده مفید از LocalStorage

* **موارد مجاز ذخیره‌سازی:** تنظیمات نمایشی کاربر (تم روشن/تیره، زبان)، پیش‌نویس فرم‌های طولانی (Draft)، و وضعیت‌های غیرحساس UI (مثلاً وضعیت باز/بسته بودن یک Sidebar).
* **ممنوعیت داده حساس:** اطلاعات حساس یا شناسایی‌کننده کاربر هرگز نباید به‌صورت متن ساده در LocalStorage نگهداری شود؛ توکن‌های احراز هویت باید طبق سیاست امنیتی پروژه (و ترجیحاً با عمر کوتاه و Refresh Token جدا) مدیریت شوند.
* **سرویس انتزاعی:** دسترسی به LocalStorage همیشه از پشت یک اینترفیس اختصاصی (مثلاً `IClientStorageService`) انجام شود، نه فراخوانی مستقیم در هر کامپوننت؛ این کار جایگزینی بعدی مکانیزم ذخیره‌سازی (مثلاً IndexedDB) را ساده می‌کند.
* **همگام‌سازی با State:** LocalStorage به عنوان منبع اولیه مقداردهی State (در `OnInitializedAsync`) استفاده شود، نه به عنوان منبع همیشگی خواندن مستقیم در حین رندر.

#### ۵. کامپوننت‌سازی حداکثری (Maximum Componentization)

* **پرهیز از کامپوننت‌های غول‌پیکر:** هر صفحه (`Page`) باید عمدتاً از ترکیب کامپوننت‌های کوچک و تک‌مسئولیتی تشکیل شود؛ منطق نمایشی مشترک هرگز نباید در چند صفحه کپی شود.
* **قرارداد ورودی/خروجی روشن:** هر کامپوننت باید ورودی‌های خود را با `[Parameter]` (و در صورت نیاز `[EditorRequired]`) و خروجی‌های تعاملی را با `EventCallback<T>` تعریف کند؛ از `CascadingParameter` فقط برای داده‌های سراسری واقعی (مانند کاربر جاری یا تم) استفاده شود.
* **کامپوننت‌های نمایشی خالص (Presentational):** تا حد امکان کامپوننت‌ها را به دو دسته «نمایشی» (بدون منطق واکشی داده) و «ظرف/Container» (مسئول واکشی داده و پاس دادن به نمایشی‌ها) تفکیک کنید تا تست و استفاده مجدد ساده‌تر شود.
* **RenderFragment و Generic Components:** برای الگوهای تکرارشونده (مانند کارت‌ها، لیست‌ها، Empty State) از `RenderFragment`/`RenderFragment<T>` و کامپوننت‌های Generic استفاده کنید تا از تکرار Markup جلوگیری شود.

#### ۶. ساختار پوشه‌بندی صفحات و کامپوننت‌ها

* **سازمان‌دهی ویژگی‌محور (Feature-Driven):** مشابه لایه Application، پوشه‌بندی پروژه Client بر اساس Feature/ماژول باشد نه نوع فایل؛ مثلاً پوشه `Features/Subscriptions` شامل صفحات، کامپوننت‌های اختصاصی و سرویس‌های Client مربوط به همان ویژگی.
* **پوشه Shared/Components:** فقط کامپوننت‌های واقعاً عمومی و بین‌ماژولی (مانند Button، Modal، LoadingSpinner، EmptyState، Pagination) در این پوشه قرار گیرند.
* **پوشه Layout:** چیدمان‌های اصلی (`MainLayout`، `AuthLayout`، `EmptyLayout`) به‌صورت مجزا نگهداری شوند.
* **هم‌جواری فایل‌های کامپوننت:** فایل‌های `.razor`، `.razor.cs` (Code-behind در صورت استفاده)، `.razor.css` و در صورت نیاز `.razor.js` هر کامپوننت باید کنار هم و در یک پوشه قرار گیرند، نه پراکنده در پوشه‌های جدا بر اساس نوع فایل.

#### ۷. استایل‌دهی: Bootstrap + Pure CSS + CSS Isolation

* **Bootstrap برای اسکلت، نه برای جزئیات:** از کلاس‌های Bootstrap فقط برای Grid، spacing و رفتارهای تعاملی پایه استفاده شود؛ ظاهر اختصاصی هر کامپوننت (رنگ، سایه، انیمیشن، حالت‌های Hover/Focus خاص) با **Pure CSS** در فایل CSS Isolation همان کامپوننت نوشته شود.
* **متغیرهای طراحی (Design Tokens):** رنگ‌ها، فاصله‌ها و شعاع گوشه‌ها را به‌صورت CSS Custom Properties در یک فایل ریشه (مثلاً `app.css`) تعریف کنید تا در فایل‌های Isolated با `var(--token-name)` استفاده شوند و یکدستی بصری حفظ شود.
* **پرهیز از Override با !important:** اگر برای غلبه بر استایل Bootstrap نیاز به `!important` مکرر است، نشانه طراحی نادرست است؛ ترجیحاً کلاس‌های سفارشی بنویسید یا کامپوننت را کاملاً با Pure CSS بازطراحی کنید.
* **استفاده حداکثری از CSS Isolation:** هر کامپوننتی که استایل اختصاصی دارد باید فایل `.razor.css` مخصوص خود را داشته باشد؛ نوشتن استایل کامپوننت‌های خاص در فایل‌های CSS سراسری ممنوع است.

#### ۸. طراحی ریسپانسیو (Responsive Design)

* **رویکرد Mobile-First:** استایل پایه برای موبایل نوشته شود و برای اندازه‌های بزرگ‌تر با Breakpointهای Bootstrap (`sm`, `md`, `lg`, `xl`) یا Media Query گسترش یابد.
* **پرهیز از اندازه‌های ثابت:** به‌جای مقادیر ثابت `px` برای عرض/فونت، از واحدهای نسبی (`rem`, `%`, `vw/vh`, `clamp()`) استفاده شود تا رفتار در دستگاه‌های مختلف روان بماند.
* **تست چندسکویی:** هر کامپوننت جدید حداقل در سه اندازه (موبایل، تبلت، دسکتاپ) و در هر دو حالت محتوای کوتاه/بلند بررسی بصری شود.

#### ۹. زبان فارسی و چیدمان راست‌به‌چپ (RTL)

* **فونت رسمی پروژه:** فونت **PeydaWeb** به‌عنوان فونت اصلی پروژه، از طریق `@font-face` با فرمت `woff2` (به همراه `font-display: swap` برای جلوگیری از پرش محتوا) در فایل CSS ریشه بارگذاری شود؛ فونت‌های Fallback مناسب (مانند Tahoma یا یک فونت سیستمی) برای زمان بارگذاری تعریف گردد.
* **جهت سند:** ویژگی‌های `dir="rtl"` و `lang="fa"` روی تگ `<html>` تنظیم شود؛ Bootstrap نسخه RTL یا فایل CSS اختصاصی RTL آن بارگذاری گردد.
* **خواص منطقی CSS (Logical Properties):** به‌جای `margin-left`/`padding-right` و مشابه آن‌ها، از خواص منطقی (`margin-inline-start`, `padding-inline-end`, و ...) استفاده شود تا کامپوننت‌ها بدون نیاز به بازنویسی در چیدمان RTL درست کار کنند.
* **اعداد فارسی/انگلیسی:** سیاست یکسانی برای نمایش اعداد در سراسر برنامه تعریف شود (معمولاً اعداد لاتین برای مقادیر عددی/پولی و اعداد فارسی صرفاً در متون توصیفی)؛ این تبدیل در یک Helper/Extension مرکزی انجام شود، نه پراکنده در هر کامپوننت.
* **تقویم شمسی:** برای انتخاب و نمایش تاریخ از یک کامپوننت Date Picker شمسی (جلالی) استفاده شود؛ تبدیل تاریخ میلادی↔شمسی در یک سرویس مشترک Client متمرکز گردد.
* **محتوای دوزبانه (فارسی/انگلیسی) در یک خط:** برای رشته‌هایی که ترکیبی از متن فارسی و اصطلاحات/کدهای لاتین هستند (مانند شماره سفارش یا ایمیل)، از `<bdi>` یا خواص Unicode-bidi مناسب استفاده شود تا جهت متن به‌هم نریزد.
* **تراز و خوانایی تایپوگرافی فارسی:** تراز پیش‌فرض متون راست‌چین باشد، `line-height` برای فونت فارسی کمی بیشتر از حالت لاتین در نظر گرفته شود و از `letter-spacing` روی متن فارسی خودداری شود (باعث شکستگی اتصال حروف می‌شود).
