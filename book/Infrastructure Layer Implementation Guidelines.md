### سند دستورالعمل پیاده‌سازی لایه زیرساخت (Infrastructure Layer Implementation Guidelines)
**هدف:** پیاده‌سازی جزئیات فنی، ارتباط با پایگاه داده، مدیریت سرویس‌های خارجی و پیاده‌سازی مکانیزم‌های احراز هویت بدون نشت (Leak) این وابستگی‌ها به لایه‌های مرکزی.
لطفاً در توسعه کلاس‌ها و ساختار این لایه، قوانین زیر را به دقت رعایت کنید:
#### ۱. پکیج‌های استاندارد لایه
 * استفاده از فریم‌ورک **Entity Framework Core** (و پروایدرهای آن مانند SQL Server) برای ارتباط با پایگاه داده.
 * استفاده از پکیج **Quartz.NET** (یا ابزارهای مشابه) برای مدیریت Background Jobها و پردازش رویدادها.
 * استفاده از **Microsoft.AspNetCore.Authentication.JwtBearer** برای تولید و مدیریت توکن‌های امنیتی.
 * استفاده از **Microsoft.AspNetCore.Authentication.Google** برای ورود و ثبت‌نام با حساب گوگل (بند ۸).
 * استفاده از **System.Net.Mail** (توکار .NET، بدون پکیج اضافه) برای ارسال ایمیل از راه SMTP (بند ۹).
 * استفاده از **Microsoft.Extensions.Options** برای پیاده‌سازی الگوی Options در مدیریت تنظیمات (Configurations).
#### ۲. پیکربندی پایگاه داده با EF Core (بدون تغییر دامنه)
 * **استفاده از Fluent API:** مپ کردن موجودیت‌های دامنه (Domain Entities) به جداول دیتابیس باید صرفاً از طریق کلاس‌هایی که IEntityTypeConfiguration<T> را پیاده‌سازی می‌کنند، انجام شود.
 * **مپ کردن فیلدهای Private:** از آنجا که Propertyهای دامنه دارای private set هستند و ممکن است فیلدهای کاملاً خصوصی (private readonly) داشته باشند، EF Core باید به گونه‌ای کانفیگ شود که بتواند این فیلدها را بخواند و بنویسد (استفاده از Property(x => x.MyProperty).HasField("_myProperty")).
 * **استفاده از Value Converters:** برای ذخیره آبجکت‌های مقدار (Value Objects) و شناسه‌های قوی (Strongly Typed IDs) در دیتابیس، حتماً از Value Converterهای EF Core استفاده کنید تا انواع پیچیده دامنه به انواع ساده دیتابیسی (مثل Guid یا string) تبدیل شوند.
#### ۳. پیاده‌سازی الگوی Repository
 * این لایه موظف است اینترفیس‌های Repository تعریف شده در لایه Application (مانند IUserRepository) را پیاده‌سازی کند.
 * **پرهیز از Generic Repository:** معمولاً از پیاده‌سازی یک Repository عمومی و بسیار بزرگ (Generic) بپرهیزید. هر Aggregate Root باید Repository مختص به خود را داشته باشد که متدهای معنا‌دار بر اساس Use Caseها در آن پیاده‌سازی شده‌اند.
 * عملیات ذخیره‌سازی نهایی (SaveChanges) معمولاً به عنوان بخشی از یک Unit of Work یا در سطح هندلرها فراخوانی می‌شود، نه مستقیماً درون متدهای Repository (Add یا Update).
#### ۴. ثبات نهایی (Eventual Consistency) و رویدادهای دامنه
 * **استفاده از Interceptorها:** برای مدیریت Domain Eventها (که در لایه دامنه تولید شده‌اند)، یک کلاس SaveChangesInterceptor از EF Core پیاده‌سازی کنید. این Interceptor پیش از ذخیره تغییرات در دیتابیس، تمام رویدادها را از موجودیت‌ها استخراج می‌کند.
 * **الگوی Outbox (Outbox Pattern):** رویدادهای استخراج شده نباید فوراً اجرا شوند. آن‌ها را به فرمت JSON سریالایز کرده و در جدولی به نام OutboxMessages ذخیره کنید (تا همراه با تغییرات اصلی در یک تراکنش دیتابیسی ذخیره شوند).
 * **پردازش پس‌زمینه:** یک Background Job با استفاده از Quartz.NET بنویسید که هر چند ثانیه یک‌بار پیام‌های پردازش نشده Outbox را خوانده و آن‌ها را توسط MediatR (به عنوان Notification) در سیستم منتشر (Publish) کند.
#### ۵. احراز هویت و زمان (Authentication & Clock)
 * **تولید توکن (Token Generation):** کلاسی مانند JwtTokenGenerator بسازید که اینترفیس IJwtTokenGenerator (از لایه Application) را پیاده‌سازی کند و وظیفه تولید توکن‌های JWT را بر عهده داشته باشد.
 * **پروایدر زمان (DateTime Provider):** هرگز در لایه‌های مرکزی از DateTime.Now یا DateTime.UtcNow استفاده نکنید. یک اینترفیس IDateTimeProvider در لایه Application تعریف کرده و در این لایه با کلاسی که DateTime.UtcNow را برمی‌گرداند، آن را پیاده‌سازی کنید (این کار تست‌نویسی را بسیار آسان می‌کند).
#### ۶. مدیریت تنظیمات (Options Pattern)
 * برای خواندن مقادیر از appsettings.json (مانند Connection Strings، تنظیمات JWT یا تنظیمات ایمیل)، کلاس‌های پیکربندی (مثلاً JwtSettings) ایجاد کنید.
 * با استفاده از IOptions<T> یا متد Bind، این تنظیمات را در زمان راه‌اندازی سیستم (Startup) اعتبارسنجی (Validate) کرده و به سرویس‌ها تزریق کنید.
#### ۷. توسعه متدهای تزریق وابستگی (Dependency Injection Registration)
 * کلاس Program.cs باید تمیز بماند. یک کلاس استاتیک به نام DependencyInjection (یا InfrastructureServiceRegistration) در این لایه ایجاد کنید.
 * یک متد اکستنشن (Extension Method) مانند AddInfrastructure(this IServiceCollection services, IConfiguration config) بنویسید و تمام ریپازیتوری‌ها، تنظیمات دیتابیس، کلاینت‌های HTTP خارجی و سرویس‌های احراز هویت را در این متد رجیستر کنید.
#### ۸. ورود و ثبت‌نام با حساب گوگل (Google SSO)
کاربر می‌تواند علاوه بر ایمیل و گذرواژه، با حساب گوگل خود ثبت‌نام کند یا وارد شود. اگر حسابی با همان ایمیل وجود نداشته باشد، اولین ورود با گوگل همان ثبت‌نام است و ایمیل چنین حسابی تأییدشده حساب می‌شود. بخش فنی این قابلیت در این لایه پیاده می‌شود (قواعد لایه‌های دیگر: بند ۸ سند Domain، بند ۸ سند Application، بند ۷ سند Presentation و بند ۱۰ سند UI):
 * **فعال‌سازی وابسته به تنظیمات:** Schemeهای گوگل فقط وقتی ثبت می‌شوند که هر دو مقدار `GoogleOAuth:ClientId` و `GoogleOAuth:ClientSecret` تنظیم شده باشند. فعال بودن قابلیت را از روی Schemeهای ثبت‌شده بخوانید (پیاده‌سازی اینترفیس IExternalSignInInfo)، نه با بررسی جداگانه تنظیمات؛ این‌طور دکمه UI، Endpointها و هندلر OAuth همیشه با هم هماهنگ می‌مانند. وقتی کلیدها تنظیم نشده‌اند، دکمه گوگل نمایش داده نمی‌شود و Endpointهای آن 404 برمی‌گردانند.
 * **دو Scheme جدا:** یک Scheme از نوع Google برای گفتگو با گوگل، و یک Cookie Scheme موقت (کوکی‌ای با نام مخصوص همین برنامه، با HttpOnly، SameSite=Lax و عمر ۵ دقیقه) به‌عنوان SignInScheme آن. این کوکی فقط هویت تأییدشده گوگل را از Callback تا مرحله نهایی نگه می‌دارد. نشست اصلی برنامه همچنان همان JWT داخل کوکی HttpOnly است و کوکی گوگل جای آن را نمی‌گیرد.
 * **مسیر Callback:** مسیر `/api/auth/google-callback` متعلق به هندلر OAuth است و همین آدرس در Google Cloud Console ثبت می‌شود. RedirectUri در Challenge باید به Endpoint جداگانه `google-finalize` اشاره کند، نه به همین مسیر. در غیر این صورت هندلر بازگشت دوم را هم یک Callback بدون state حساب می‌کند و ورود با خطای `The oauth state was missing or invalid` شکست می‌خورد.
 * **Claim تأیید ایمیل:** فیلد `email_verified` پاسخ گوگل را با `ClaimActions.MapJsonKey` به Claim تبدیل کنید. لایه Application بدون این مقدار نمی‌تواند تصمیم بگیرد که حساب را بر اساس ایمیل وصل کند یا نه.
 * **کوکی Correlation:** مقدار SameSite آن را Lax بگذارید. مقدار پیش‌فرض None روی http (محیط توسعه) توسط مرورگر دور ریخته می‌شود و خطای `Correlation failed` می‌دهد.
 * **خطاهای سمت گوگل:** رویداد OnRemoteFailure را پیاده کنید تا انصراف کاربر، state منقضی‌شده یا خطای تبادل کد به‌جای خطای 500، با ثبت لاگ به `/login?google_error=failed` هدایت شود.
 * **کلیدهای Data Protection:** کوکی‌های state و correlation با Data Protection رمز می‌شوند. کلیدها را با نام ثابت برنامه (SetApplicationName) در پوشه `keys` کنار برنامه نگه دارید (PersistKeysToFileSystem). روی هاست اشتراکی، کلیدهای درون‌حافظه با هر Recycle شدن App Pool از بین می‌روند و ورودِ نیمه‌کاره با `Correlation failed` شکست می‌خورد. پوشه `keys` به دسترسی نوشتن و حذف نیاز دارد؛ برنامه هنگام راه‌اندازی یک فایل آزمایشی می‌نویسد و پاک می‌کند و اگر نتوانست، با یک هشدار به کلیدهای موقت برمی‌گردد تا خطای دسترسی کل سایت را از کار نیندازد.
 * **پراکسی و Forwarded Headers:** آدرس redirect_uri از Scheme و Host درخواست ساخته می‌شود. پشت پراکسی‌ای که TLS را خاتمه می‌دهد، UseForwardedHeaders باید اولین Middleware باشد تا این آدرس همان آدرس https عمومی شود. فقط به پراکسی‌های فهرست‌شده در `ForwardedHeaders:KnownProxies` و `ForwardedHeaders:KnownNetworks` اعتماد کنید (پیش‌فرض فقط loopback است).
 * **نگهداری اسرار:** ClientSecret هرگز وارد Git نمی‌شود. در محیط توسعه از user-secrets و در سرور از فایل `appsettings.Production.json` (که در .gitignore است) یا متغیرهای محیطی مانند `GoogleOAuth__ClientSecret` استفاده کنید.
 * **تنظیم در Google Cloud Console:** یک OAuth Client از نوع Web application بسازید و آدرس `https://<host>/api/auth/google-callback` را به‌عنوان Authorized redirect URI ثبت کنید. برای توسعه، آدرس `http://localhost:<port>/api/auth/google-callback` را هم اضافه کنید؛ پورت محلی برنامه در launchSettings.json باید با همین آدرس یکی باشد.
#### ۹. ارسال ایمیل (SMTP)
 * **پیاده‌سازی ساده و بدون پکیج:** IEmailSender را با System.Net.Mail.SmtpClient پیاده کنید. برای هر ارسال یک SmtpClient تازه بسازید و UseDefaultCredentials = false بگذارید تا هویت ویندوزی App Pool هرگز فرستاده نشود. متن ساده را بدنه اصلی و HTML را AlternateView کنید و سرآیند Auto-Submitted: auto-generated را اضافه کنید تا پاسخ‌گوهای خودکار جواب ندهند.
 * **تنظیمات با الگوی Options:** بخش `Smtp` با کلیدهای Host، Port، EnableSsl، Username، Password، FromAddress، FromName و TimeoutSeconds. در راه‌اندازی اعتبارسنجی کنید؛ مثلاً اگر Host تنظیم شده، FromAddress باید نشانی ایمیل معتبر باشد.
 * **هاست اشتراکی پلسک:** ساده‌ترین راه، سرور ایمیل خود هاست است: Host = localhost، Port = 25، بدون SSL و بدون نام کاربری. سرور ایمیل پلسک معمولاً ایمیلِ برنامه‌های همان سرور را بدون ورود می‌پذیرد. اگر نپذیرفت، در پلسک یک صندوق ایمیل (مثلاً `no-reply@<domain>`) بسازید و با Port = 587، EnableSsl = true و نام کاربری و گذرواژه همان صندوق بفرستید. نشانی فرستنده باید روی دامنه‌ای باشد که همان سرور میزبانی می‌کند و سرویس ایمیلش در پلسک روشن است؛ وگرنه ایمیل رد می‌شود یا به هرزنامه می‌رود.
 * **پورت ۴۶۵ پشتیبانی نمی‌شود:** SmtpClient فقط STARTTLS را می‌شناسد، نه TLS ضمنی. پورت 465 را در اعتبارسنجی Options رد کنید تا خطا هنگام راه‌اندازی دیده شود، نه در اولین ایمیل.
 * **بدون تنظیمات SMTP:** اگر Host خالی است، در محیط Development کل ایمیل (همراه کد) در لاگ نوشته شود تا جریان در محیط محلی قابل آزمایش باشد. در هر محیط دیگری فقط یک خطا لاگ شود و ارسال شکست بخورد. کد هرگز در لاگ Production نوشته نشود؛ حتی عنوان ایمیل را که کد دارد، پیش از لاگ کردن بپوشانید.
 * **خطاهای ارسال:** SmtpException، InvalidOperationException و IOException را بگیرید، با جزئیات لاگ کنید و Error.Failure برگردانید.
 * **اسرار:** گذرواژه صندوق ایمیل هم مثل بقیه اسرار بیرون از Git نگهداری می‌شود.
#### ۱۰. اعتبار نشست و الزام تأیید ایمیل
 * **مهر امنیتی در توکن:** JwtTokenGenerator مهر امنیتی کاربر را به‌صورت یک Claim (مثلاً stamp) در توکن می‌گذارد.
 * **بررسی نشست در هر درخواست:** در رویداد OnTokenValidated از JwtBearer، کاربر را با یک کوئری سبک (AsNoTracking و فقط مهر امنیتی و وضعیت تأیید) از پایگاه داده بخوانید. اگر حساب وجود ندارد یا مهر امنیتی فرق می‌کند، context.Fail را صدا بزنید تا درخواست 401 بگیرد. لغو درخواست از طرف مرورگر (RequestAborted) را بی‌صدا با Fail تمام کنید تا لاگ خطا پر نشود.
 * **وضعیت تأیید از پایگاه داده، نه از توکن:** Claim وضعیت تأیید ایمیل را در همین رویداد از روی پایگاه داده اضافه کنید و هر Claim هم‌نامی را که در توکن باشد حذف کنید. این‌طور تأیید ایمیل بدون صدور توکن تازه، فوراً در همه نشست‌های باز اثر می‌کند.
 * **Policy پیش‌فرض:** DefaultPolicy را طوری تعریف کنید که علاوه بر کاربر واردشده، Claim تأیید ایمیل را با مقدار true بخواهد. این‌طور هر [Authorize] ساده خودبه‌خود تأیید ایمیل را هم می‌خواهد. یک Policy نام‌دار جدا (مثلاً AllowUnconfirmedEmail) فقط کاربر واردشده را می‌خواهد و روی Endpointهای تأیید ایمیل و اطلاعات کاربر جاری گذاشته می‌شود.
 * **ستون‌های تازه در پایگاه داده موجود:** اگر پروژه به‌جای Migration از EnsureCreated استفاده می‌کند، این متد پایگاه داده موجود را تغییر نمی‌دهد. برای ستون‌های تازه (وضعیت تأیید، مهر امنیتی و کدها) پایگاه داده موجود را با Migration یا اسکریپت به‌روز کنید و برای حساب‌های قدیمی تصمیم بگیرید. معمولاً حساب‌هایی که پیش از این قابلیت ساخته شده‌اند تأییدشده حساب می‌شوند و هر کدام یک مهر امنیتی تصادفی می‌گیرند.
**چک‌لیست تایید کد (Code Review Checklist):**
 * [ ] آیا تمام کانفیگ‌های دیتابیس با استفاده از Fluent API نوشته شده و کلاس‌های دامنه دست‌نخورده باقی مانده‌اند؟
 * [ ] آیا اینترفیس‌های لایه Application به‌درستی و بدون استفاده از منطق بیزینسی (Business Logic) پیاده‌سازی شده‌اند؟
 * [ ] آیا رویدادهای دامنه (Domain Events) از طریق Interceptorها و مکانیزم Outbox ذخیره و پردازش می‌شوند؟
 * [ ] آیا ارتباط با سرویس‌های شخص ثالث (Third-party) به‌درستی کپسوله شده و در صورت بروز خطا لاگ می‌شود؟
 * [ ] آیا ثبت وابستگی‌های این لایه (DI) در یک Extension Method اختصاصی انجام شده است؟
 * [ ] آیا مقادیر تنظیمات (Settings) از طریق الگوی Options به کلاس‌ها تزریق شده است؟
 * [ ] آیا Schemeهای گوگل فقط با تنظیم بودن ClientId و ClientSecret ثبت می‌شوند و فعال بودن قابلیت از روی Schemeهای ثبت‌شده خوانده می‌شود؟
 * [ ] آیا ClientSecret و سایر اسرار بیرون از Git (user-secrets، فایل Production نادیده‌گرفته‌شده یا متغیر محیطی) نگهداری می‌شوند؟
 * [ ] آیا ارسال ایمیل خطا را به‌صورت ErrorOr برمی‌گرداند و کدهای یک‌بارمصرف هرگز در لاگ Production نوشته نمی‌شوند؟
 * [ ] آیا Policy پیش‌فرض تأیید ایمیل را می‌خواهد و هر نشست در هر درخواست با مهر امنیتی سنجیده می‌شود؟
